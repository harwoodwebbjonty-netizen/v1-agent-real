## 1. Tenant architecture

**Confirmed: there is no multi-tenant concept anywhere in this codebase.** A repo-wide grep for `workspace|tenant|organi[sz]ation_id|company_account|multi-tenant` across `backend/app` returns zero hits. The schema (33 tables, `backend/app/db.py`) has exactly one `users` table with no `org_id`/tenant column on it or on any child table — every table scopes to `owner_user_id`/`user_id` within one single shared instance. This is not a partially-built multi-tenant system with gaps to close; it is architecturally a **single-tenant application**, full stop. Every item below in this section is therefore "does not exist" rather than "exists but incomplete," and is listed to make that explicit rather than to imply near-term work:

- Organisation/workspace model: **absent**.
- Tenant IDs / data boundaries / tenant-aware queries: **absent** — there is nothing to scope by.
- Cross-tenant leakage risk: **not applicable in the traditional sense**, but see the closely related and very real risk below.
- Organisation ownership, user invitations (in the SaaS sense of "invite someone into *your* company's workspace"): **absent**. What exists instead is an admin-only, single-shared-roster model: `POST /users` + `POST /users/{id}/set-password` (`users.py`), gated by `require_permission("manage_team")` — an admin creates every account by hand; there is no self-serve signup, no email-based invite link, no org boundary to invite *into*.
- Custom roles/permissions: **this part genuinely exists and is well-built** — a real RBAC layer (`roles` table, `backend/app/services/permission_service.py`, `backend/app/routers/roles.py`) with per-role permission sets and a `lead_scope` concept, all correctly enforced via `require_permission(...)` dependencies (verified: 0 accidental gaps across 124 routes, see §4). This is a legitimate foundation to build an org-scoped permission model on top of later — it's the tenant boundary itself that's missing, not the permission model.
- Workspace switching, account offboarding, tenant-level settings/feature-flags, per-tenant integration credentials: **absent** — none of these have anywhere to attach to, since there is no tenant object.

**The closely-related real risk today**: the product's actual current design is a **single shared lead pool visible to every user of the one deployment** — documented in this repo's own `CLAUDE.md` as "deliberate." That's a reasonable choice for one company's internal sales team sharing one deployment. It becomes a serious problem the moment two *different customer businesses* are ever put on the same running instance without building real tenant isolation first — every lead, email draft, call log, and win-back campaign from Company A would be visible to every user at Company B. **This is the single most important fact for the SaaS-readiness verdict**: the product cannot safely take on a second customer organisation on shared infrastructure today, under any circumstances, without tenant-scoping work — not as a "nice to have before scaling," but as a hard precondition.

## 2. SaaS account lifecycle

| Capability | Status | Evidence |
|---|---|---|
| Self-serve registration | **Absent by design** | `auth.py:29-83` (`identify`): self-registration is explicitly closed — only the very first account on a fresh deployment can be created this way (bootstrap-token gated); every other account requires an existing admin. This was a deliberate security fix (see this repo's own decision log — closing an earlier self-registration hole). |
| Email verification | **Absent** | No email-sending-on-signup code path found; accounts are name+password only, no email field captured at account creation at all in the schema reviewed. |
| Login | **Present, solid** | Name+password, bcrypt-equivalent PBKDF2 hashing (`auth_service.py`), rate-limited (`auth_rate_limit`, stricter than general endpoints), account lockout after repeated failures (`login_max_attempts`/`login_lockout_minutes`). |
| Password reset (self-service) | **Absent** | No "forgot password" flow found — only an admin-driven `set_user_password` route. Fine for a small trusted internal team; a real gap for any SaaS customer's own end users. |
| Session handling | **Present, correct** — bearer tokens, 30-day TTL, server-side revocation on logout/password-change (`delete_other_sessions_for_user`). This session's own conversation (this audit run) independently root-caused and fixed a related UX gap (no auto-detection of a dead session) as a prior task this session — see git log `v0.6.11`. |
| Organisation creation | **Not applicable** — no org concept. |
| Onboarding flow | **Absent** as a guided flow; the product works immediately once an account exists. |
| Invite acceptance | **Absent** — accounts are admin-created with a password set directly, not an emailed invite link the recipient completes. |
| Trial lifecycle, subscription status, billing states, usage limits (as *billing*), plan entitlements, upgrade/downgrade, cancellation, account deletion, failed-payment handling | **All absent** — confirmed zero references to Stripe, billing, subscription, or plan-tier anywhere in `backend/app`. **Usage limits do exist**, but as internal cost control, not billing: the credit-limit system (`credit_settings.py`, `credit_usage` table) caps each user's *AI-feature spend* per month (e.g. £20 default for phone lookup, £250 for win-back) — this is real, working, and audited (see §3) but it is a cost-containment mechanism for the operator's own Anthropic bill, not a monetization/plan-gating mechanism for paying customers. |

**Net**: the account lifecycle is well-built for "one trusted team, admin adds people by hand" and has essentially none of the self-serve SaaS lifecycle (signup → trial → paid → invite teammates → billing) a commercial multi-customer product needs. None of this is a defect in what exists — it's simply evidence the product was never built to be sold as self-serve SaaS, which reframes "what's missing" as "an entire lifecycle layer to add," not "bugs to fix."

## 3. Operational scalability

- **Pagination**: **confirmed absent on the majority of list endpoints.** The coded evaluation (`audit/results/backend_routes.json`) flags 22 GET endpoints with no `limit`/`offset`/`cursor` parameter; manually verified on the two most important ones — `GET /leads` (`leads.py:242-247`, calls `db.list_all_leads_for_user(...)` unbounded) and `GET /users` (`users.py:28-31`, calls `db.list_users()` unbounded). At today's data volume (order of ~1,000 leads per this repo's own tracked project state) this is invisible in practice; it is a real ceiling that will start to hurt well before any multi-tenant growth scenario, since every tenant added multiplies total row counts against the same unbounded queries.
- **Missing indexes**: 19 real (non-primary-key) foreign-key-shaped columns have no explicit index (`audit/results/schema_index_scan.json`), most notably `lead_phones.lead_id` and `lead_emails.lead_id` — both queried on every single lead-record render. Low urgency today given current row counts, real before any serious growth.
- **Single-worker deployment, by design and explicitly documented in-code**: `sequences_service.py`'s own module docstring states its correctness "is correct for the single-worker systemd deployment this backend actually runs under... running multiple uvicorn workers would need a real lock." Confirmed via the systemd unit: no `--workers` flag. This has three concrete consequences: (1) the three in-process `asyncio` background loops (sequence scheduler, activity refresh, CH filing stream — all well-built individually, see the Integrations doc) have nowhere to coordinate if ever run multi-process; (2) the rate limiter (`slowapi`, `MemoryStorage`, confirmed in-process/in-memory, no `storage_uri`) resets to zero on every restart and would silently stop being a *global* limit the moment the deployment scales to multiple workers, each keeping its own independent counter; (3) there is a real ceiling on concurrent-request throughput inherent to one Python process handling everything, including long-running AI calls.
- **AI task handling**: cost is genuinely well-controlled (see §4) and one AI feature (`sales_intelligence_service.py`) has direct documented evidence of the team already fixing a real cost-blowout incident by removing open-ended tool use entirely rather than trying to cap it — a strong, specific signal of engineering maturity on this exact axis. Long-running AI calls are not queued/backgrounded with a job system, though the sequence scheduler and activity refresh loops do function as a lightweight background-job mechanism for their specific use cases.
- **Provider failures**: Companies House 429s are caught via a dedicated `CHRateLimitError` and handled gracefully at every call site (confirmed 4 call sites); OAuth token refresh failures raise but don't crash callers. This is genuinely solid provider-failure handling for the two most-exercised external dependencies.
- **Observability**: **confirmed absent** — no APM/error-tracking service (Sentry, Datadog, Rollbar, Bugsnag, etc.) is integrated anywhere in `backend/` or `app/` (checked `requirements`-equivalent config, `package.json`, `Cargo.toml`, source grep — zero hits). The only logging is Python's stdlib `logging` module writing to whatever captures stdout (in production, the systemd journal, accessed via `journalctl` — which is how this very audit diagnosed an unrelated session-expiry bug earlier in this working session). There is no structured logging, no request tracing, no dashboarding, and no alerting of any kind. **If the backend silently starts erroring for a subset of users at 3am, nobody finds out until someone notices manually.**
- **Backups & disaster recovery — an active, unrelated-to-multi-tenancy operational risk, confirmed by direct (read-only) inspection of the VPS**:
  - `team.db` grew from **58MB to 1.68GB in one month** (12 Jul → 12 Aug), a ~29x increase, and was still growing at time of writing.
  - **No cron job is installed for either `root` or `appuser`** on the VPS — `backend/deploy/backup.sh`, a well-written script that would automate nightly gzip'd, pruned backups, exists in the repo but was never actually installed as documented in its own header.
  - 10 uncompressed backup snapshots exist on disk (7.3GB total), dated 12 Jul–7 Aug, produced by the ad hoc Python `backup_database()` helper rather than the cron-intended shell script — evidence these were triggered manually, not on a schedule.
  - **No backup exists from the last 5 days** as of the time of writing. A single bad migration, disk fault, or accidental delete right now loses up to 5 days of every customer-facing record in the system.
  - VPS disk headroom is currently fine (87GB total, 15% used) — not an imminent outage, but the growth trajectory combined with zero backup automation and zero disk-usage alerting is a real, present-tense risk independent of any SaaS ambitions. **This is a P0 item for the current single-tenant deployment as it stands today**, separate from and prior to any multi-tenancy work.
  - The *cause* of the growth is **Inferred, not Confirmed** — this audit was blocked by this environment's own safety controls from running even a read-only row-count query against the production database, so the exact table breakdown is unverified. The most plausible driver, based on this repo's own tracked project history, is the Companies House charge feed, which recently started ingesting significantly more volume after an unrelated key-configuration bug was fixed. A direct table-size breakdown is the concrete next step and needs either explicit user sign-off to query the production DB, or the user running a one-off `.dbinfo`/`dbstat` pass themselves.
- **Migration strategy**: genuinely solid — 31 sequential, append-only migrations (`CURRENT_SCHEMA_VERSION = 31`), applied automatically on backend restart, never editing shipped migrations (confirmed as a stated and followed rule). This is a real strength to preserve.
- **API versioning**: **absent** — there is no `/v1/` prefix or version header anywhere; every endpoint is implicitly "current only." Not a problem for a single first-party client (the Tauri app is always built against the exact backend it ships with), but would need addressing before any external/public API surface (see Integrations doc).

## 4. Security and trust

This section is substantially informed by a dedicated, very thorough integrations/security research pass (full detail in that agent's findings, folded in here) plus this audit's own independent verification.

**Strengths, confirmed**:
- **Zero accidental unauthenticated endpoints** across all 124 routes in 20 routers — every route has a real auth dependency except three deliberately public ones (login, the pre-auth login-picker's name+avatar-only endpoint, and the OAuth callback), all independently verified appropriate.
- **SQL injection**: parameterized queries throughout; the two dynamic-`SET`-clause query builders that interpolate column *names* (never values) are either guarded by an explicit allowlist regex (`_assert_safe_columns`, referencing a prior internal audit finding "audit L4") or, where unguarded, only ever called with hardcoded dict keys, never request-derived ones — confirmed by tracing every call site. One consistency gap: two of these builders (`update_prospecting_run`, `update_enrollment`) don't have the same `_assert_safe_columns` guard `update_lead_fields` does — currently safe only because of caller discipline, not because the function itself enforces it. Worth closing for defence-in-depth, low urgency given the current call sites.
- **OAuth CSRF protection**: correctly implemented (`secrets.token_urlsafe(24)` state nonce, server-side, single-use) for the one OAuth integration that exists (email send). This is the right pattern to reuse for calendar/telephony OAuth later rather than reinvent.
- **No hardcoded/committed secrets anywhere in the repo or git history** (verified independently by this audit's own scripted scan in addition to the security research pass — zero hits for `sk-`/`AKIA`/`xox*`-shaped patterns, and `.env` has never been committed at any point in git history for either the root or `backend/` gitignore scope).
- **CORS**: empty allow-list by default (`main.py`) — correct, since the Tauri app talks to the backend via native `reqwest`, not a browser, so CORS is genuinely just defence-in-depth here, not a live control surface.
- **AI/prompt-injection surface**: no classic system-prompt injection vector exists (user data is never concatenated into a `system=` string across all 8 Anthropic-calling service files, confirmed). A more subtle, architectural indirect-injection surface exists in the 2-3 features that give the model live web-browsing tools, but it's meaningfully bounded by hard `max_uses` caps and a strict, tool-free, schema-enforced final extraction step — and one feature (`sales_intelligence_service.py`) has direct evidence the team already identified and closed a related cost-blowout risk by removing tool use entirely rather than trying to cap it, which is a strong positive signal about how this team responds to this exact class of risk.
- **Credit/cost limits**: real, enforced (`check_credit_limit` → HTTP 402 before the paid call, `record_credit_spend` after), consistently applied. A minor non-atomic check-then-act race exists under concurrent identical requests from the same user, bounded in practice by low per-feature costs (£0.02–£0.16) — low severity.

**Gaps, confirmed**:
- **OAuth access/refresh tokens stored in plaintext** in `email_oauth_accounts` — no encryption-at-rest layer exists anywhere in the codebase (zero hits for `encrypt|fernet|kms|vault`). Anyone with read access to `team.db` — including anyone who obtains one of the unencrypted backup copies currently sitting on the VPS (§3) — has a live, working credential into a real connected Gmail/Microsoft account. **This is the highest-priority confirmed security finding in the entire audit.**
- **Audit log coverage is real but uneven**: role changes and credit-limit changes (the two most governance-sensitive settings) are consistently logged with a genuine, queryable `audit_log` table — a real strength, not just a timestamp column. But user creation, user deletion, password resets by an admin, and the *entire* outbound-email-sending surface (win-back sends, email-writer sends, list-campaign sends, sequence enrollment) have zero audit trail. Given the product's own design deliberately shares one lead pool across all users, and there's no "who viewed this record" logging at all (only "who changed it," and only for the mutation types that do call `record_audit`), a security incident investigation today could not answer "did anyone read/export sensitive lead data they shouldn't have."
- **No admin-impersonation / secure-support-access model exists** — not applicable yet at single-tenant scale, but would need designing before any SaaS support team needs to help a customer inside their own workspace.
- **No encryption-at-rest for the database file itself** — SQLite on disk, unencrypted, on the VPS; combined with the plaintext-token finding above, this compounds the exposure of a single disk-level compromise.
- **UK GDPR considerations**: no data-retention policy, no data-export-for-a-user tooling, no right-to-erasure flow, and no documented lawful basis/processing register found anywhere in the repo. For a product handling real prospect/lead personal data (names, phone numbers, emails) on behalf of a UK sales team, this is a real, unaddressed compliance gap independent of the multi-tenancy question — it applies to the *current* single-customer deployment already.

## 5. Consolidated P0 launch blockers

These block *any* external paying customer, in priority order, independent of each other:

1. **No multi-tenant data isolation exists at all** (§1) — the single highest-severity blocker; nothing else here matters if a second customer's data could ever end up visible to the first.
2. **Production database has no working backup automation and is growing rapidly with an unconfirmed cause** (§3) — a present-tense operational risk to the *current* single-tenant deployment, not a future one; fix regardless of SaaS plans.
3. **OAuth tokens stored in plaintext** (§4) — a real, exploitable-on-disk-compromise credential exposure that gets worse, not better, once there are more customers' connected email accounts to protect.
4. **No self-serve account lifecycle** (§2) — signup, billing, invites, trial/plan gating all need to be built from zero; this is the largest single unit of *new* engineering work in the whole audit, not a fix to existing code.
5. **No observability/alerting** (§3) — launching to external customers with zero error-tracking or uptime alerting means the first the team learns of an outage is a customer complaint.
6. **GDPR data-handling gaps** (§4) — retention, export, and erasure tooling needed before onboarding any customer's real prospect data under UK data-protection law.

Everything else in this document (pagination, indexes, audit-log coverage, API versioning, admin impersonation) is real and worth fixing, but is P1/P2 — important for a *credible, scaled* SaaS launch, not a hard blocker for the first one.
