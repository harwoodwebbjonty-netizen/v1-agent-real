# 05 — Visual & UX Forensic Audit

Repo: `/Users/jontyhw/v1 agent` · Commit: `8c923ac5e703928e3f94721e6c11593a5c397f7d` · Evaluated: 2026-08-12

Method note: this is a native Tauri desktop app, not a website — there is no live browser to screenshot without building and launching the compiled binary, which was judged out of proportion to this audit's read-only mandate. Findings below come from direct source/CSS inspection (a dedicated research pass reading `app/src/style.css`, `dashboard-polish.css`, and every view/component file, cross-checked against this audit's own independent grep scan in `audit/results/misc_scans.json`) rather than rendered screenshots. Every count below is a real, reproducible grep/count, not an impression.

## 1. The single biggest reason it feels homemade: dead/unreachable screens

Before any styling critique — this is the most consequential finding in the entire visual/UX audit, and it's structural, not cosmetic.

**Finding 05-01**
- **What's wrong**: `app/src/tabs.ts` declares 15 `ViewName`s and wires an `init*()` call for all of them in `main.ts`, but `app/src/router.ts`'s `ALL_VIEWS` array — the thing that actually toggles which `#view-*` container is visible — only lists 10. **Call Queue, Opportunity Workspace, and AI Sales Intelligence are fully built (real data fetching, real empty states, real error handling via `showToast`) but structurally unreachable**: no sidebar link targets them, the router never shows their containers, and the one cross-view handoff that could open Opportunity Workspace (`setPendingOpportunityWorkspaceLead()`) is exported but never called anywhere in the codebase.
- **Why it feels unprofessional**: a shipped product with three complete, polished features nobody can open is exactly the kind of thing that happens in a fast-moving internal tool and essentially never survives in a commercial SaaS product's QA process. It's invisible to end users today (they simply can't find something they don't know exists), but it's a strong signal to anyone auditing the codebase — like this one — that navigation/IA hasn't been kept in sync with what's actually built, which is the same underlying failure mode that produces the "jumbled" feeling in general.
- **User impact**: none directly (they can't reach it) — but it represents real, already-paid-for engineering value sitting inert, and it means opportunity-stage management (a core pipeline concept, see the Feature Gap Matrix) has no working UI path at all despite `opportunity_stage` existing as a first-class field on every lead.
- **Exact location**: `app/src/tabs.ts:1-16` (declares all 15) vs `app/src/router.ts:3-14` (`ALL_VIEWS`, only 10) vs `app/src/main.ts:35-51` (all 15 `init*()` calls fire regardless).
- **Design-system correction**: not a styling fix — either wire the three back into `ALL_VIEWS` + a nav entry (if this was an unintentional regression from a past refactor), or delete the dead code/containers/init calls entirely (if the features were deliberately paused) — see `charge-feed`/`chargeFeed.ts` for what an intentional, cleanly-documented deprecation looks like in this same codebase (`initChargeFeed(): void { /* no-op */ }` with an explicit comment explaining the merge into Activity Feed). Right now the three orphaned screens look exactly like `charge-feed` from the outside (an `init*()` call and a hidden container) but are not documented the same way, which is itself confusing for a future engineer.
- **Local or systemic**: **systemic** — it's a navigation/routing architecture gap (two independently-maintained view lists that can silently drift), not a one-off mistake in one file.

**Finding 05-02** — related, smaller: three nav links (AI Prospecting, Win-back, Settings) carry a `data-admin-only="true"` HTML attribute (`app/index.html:36,63,82`) that **no TypeScript file ever reads** — confirmed by a repo-wide grep returning only those three HTML occurrences. Actual gating runs entirely through permission strings (`NAV_PERMISSIONS` in `tabBar.ts`), so a non-admin member granted the relevant permission *will* see these sections despite the markup implying an admin-only hard gate. This is stale, misleading markup — low user impact (the real permission check does work correctly), but exactly the kind of small inconsistency that compounds into "does anyone actually know how this app works" across a larger team.

**Finding 05-03** — Settings has a *second*, redundant access-control layer: a device-local, SHA-256-hashed PIN stored in `localStorage`/`sessionStorage` (`tabBar.ts:38-125`), checked entirely client-side with no backend involvement, layered on top of the real permission-based nav gating. This PIN is not tied to user identity at all — it's one shared secret per browser profile. **Design-system correction**: remove it; the permission system it duplicates is the correct, already-working mechanism, and a second, weaker, client-only gate in front of the same door is confusing rather than additive security.

## 2. Information architecture

- **Routing is tab-based, not URL-based** — reasonable for a Tauri desktop shell, but it means there's no deep-linking, no browser back/forward, and (per §1) two independently-maintained lists of "what views exist" that can silently drift apart.
- **Permission gating is nav-level only, not sub-view-level**, by explicit design (`tabBar.ts:5-6` comment confirms this): the three Outreach sub-tools (Email Writer, List Campaign, Sequences) share one `view_outreach` permission — there's no way to grant a rep Sequences without also granting Email Writer and List Campaign. This may be an intentional simplification, but it's worth confirming as a deliberate product decision rather than an oversight, since the RBAC system underneath is otherwise granular (per-permission, not per-role-tier).
- **Only two screens** (Cold Call Lists, Settings) implement any internal-to-the-screen permission logic beyond the nav link; every other screen is all-or-nothing once a user can open it at all.
- **Discoverability of secondary features is uneven, but not obviously broken** given the systemic gap in §1 — the ten reachable top-level nav sections map reasonably cleanly to the ten real jobs a rep/admin does day to day (Today, Leads, Cold Call Lists, Activity Feed, Outreach, Win-back, Calendar, Analytics, AI Prospecting, Settings). The IA problem in this product is not "too many competing destinations" (a common SaaS-bloat failure mode covered in the competitor benchmark, e.g. Zoho/Salesforce) — it's the opposite: a handful of real, finished destinations that fell out of the map entirely.

## 3. Design-system consistency

The token system itself (`style.css:33-141`) is genuinely well-designed on paper: 72 custom properties, an 8-step spacing scale, a 6-step type scale, documented status colors, and — notably — a deliberate, well-commented backward-compatibility shim (`style.css:66-83`) mapping 10 legacy token names forward so old rules don't silently break. That comment is itself evidence of a team that has cared about this system's integrity over time. The problem is not the system's design; it's how consistently the codebase actually uses it.

**Finding 05-04 — the type scale is bypassed more often than it's used**
- **What's wrong**: of 213 `font-size` declarations in `style.css`, **123 (58%)** use a raw value instead of one of the six `--text-*` tokens. Those raw values aren't even a small, deliberate secondary set — they fragment into 20+ distinct one-off sizes (`0.72rem` ×14, `0.78rem` ×13, `0.85rem` ×12, `0.82rem` ×11, `0.75rem` ×9, `0.7rem` ×7, `0.8rem` ×6, `0.9rem` ×5, `0.62rem` ×5, plus a dozen others appearing 1-4 times each).
- **Why it feels unprofessional**: this is precisely the mechanism by which a UI ends up feeling like "a lot of slightly-different-sized text everywhere" rather than a small number of deliberate hierarchy levels — the exact "why does it feel jumbled" question this audit was commissioned to answer has a direct, countable answer here.
- **User impact**: subtle but real — inconsistent type hierarchy makes scanning harder (the brain can't rely on "this size = this level of importance" once there are 20+ sizes instead of 6).
- **Exact location**: `app/src/style.css`, distributed across the whole 4,800+-line file (not concentrated in one component).
- **Design-system correction**: an audit-and-consolidate pass mapping each of the 20+ raw sizes to its nearest `--text-*` token, done as pure refactor (no visual redesign needed first) — see the roadmap for sequencing.
- **Local or systemic**: **systemic** — spread across essentially the whole stylesheet, not a handful of components.

**Finding 05-05 — `padding`/`border-radius` show the same pattern at a smaller scale**: 45+ of 147 `padding` declarations (31%) and 46 of 119 `border-radius` declarations (39%) bypass their respective tokens, with `border-radius` fragmenting into at least ten undocumented radii beyond the two official ones (9px, 13px) — `8px`×6, `3px`×6, `999px`×5 (a defensible pill-shape idiom), `5px`×3, `4px`×3, `7px`×2, `20px`×2, `10px`×2. Same correction pattern as 05-04, lower priority (smaller visual impact than type-scale drift). **Systemic.**

**Finding 05-06 — a later-added file has a higher bypass rate than the one it extends**: `dashboard-polish.css` (136 lines, loaded immediately after `style.css`) contains 54 raw px values and opens its own three-property `:root` block that mostly aliases back to `style.css` tokens without those aliases actually being used in the file's own rules. This is worth flagging specifically because it shows the drift is *accelerating*, not just historical — the newest CSS file added to the project has a denser concentration of the same problem than the codebase average.

**Finding 05-07 — inline styles, ~104 occurrences across 15 view files**, concentrated in `aiProspecting.ts` (21), `winBackCampaign.ts` (17), `settings.ts` (17), `analytics.ts` (12). Roughly half correctly reference `var(--space-*)` (a maintainability smell — belongs in a CSS class, not inline, but not a token violation) and half use genuinely off-scale raw values (`14px`, `16px`, `34px`, `76px`, `90px`, `96px`, `150px`, `240px`, `280px`, `320px` — none match the 8-step spacing scale). **Local to the listed files, but the pattern itself (reach for an inline style rather than a class) is systemic.**

**Finding 05-08 — a hardcoded fallback color that contradicts its own token**: `identitySwitcher.ts:40` and `tabBar.ts:62` both write `color:var(--danger,#e53)`. `--danger` is always defined (`#E31346`, the brand crimson) — the `#e53` fallback (an orange-red) would never actually render today, but it's a visibly *wrong* value sitting in the code (doesn't match the design system's actual danger color at all), which is the kind of small inconsistency that erodes confidence in the codebase's overall care level once found. **Local, trivial fix.**

**Finding 05-09 — an undocumented 10-color micro-palette for nav icons**: `style.css:397-406` hardcodes ten distinct per-section sidebar icon colors directly in attribute selectors (e.g. `#10b981`, `#8B5CF6`, `#f97316`), none of which exist as named custom properties anywhere in the file. CLAUDE.md's own design documentation states the current nav icon system is "uniform thin grey line icons... crimson only when active — no more per-section icon colours" — **this CSS block appears to be dead/superseded code left over from a pre-redesign icon scheme**, not an active inconsistency a user would see, but worth confirming and removing since it currently reads as a contradiction between the documented design system and the CSS on disk. **Local, needs a quick live-render check to confirm it's truly unused before deletion.**

**Finding 05-10 — chart colors hardcoded outside the token system**: `analytics.ts:270,271,321,344,435` hardcode six hex values directly into Chart.js config (including the brand accent `#E31346` as a literal string) instead of reading the CSS custom property at render time. These happen to match the current token values today, but nothing keeps them in sync — a future rebrand or dark-mode pass would visually desync the charts from the rest of the UI, since Chart.js output doesn't participate in the `[data-theme="dark"]` cascade at all the way CSS-styled elements do. **Local to `analytics.ts`, but architecturally instructive**: this is the one place in the app where the "single source of truth in `:root` token values" principle CLAUDE.md documents genuinely cannot be honored without extra plumbing (reading `getComputedStyle` at render time), because Chart.js needs literal color strings, not CSS variables.

## 4. Duplicate component patterns (systemic, no shared component library)

**Finding 05-11 — at least four independent hand-rolled modal/overlay implementations**, and no `modal.ts`/`dialog.ts` exists in `app/src/components/` at all (confirmed: the directory holds `activityModal.ts`, `industryFilter.ts`, `leadTable.ts`, `multiSelect.ts`, `sidePanel.ts`, `tabBar.ts`, `topBar.ts` — no generic overlay primitive):
1. Static markup in `index.html`, toggled via `classList.remove/add("hidden")` (`activityModal.ts`).
2. `document.createElement` + manual class + `body.appendChild`, reusing the class name `conflict-modal-overlay` — independently reimplemented in **four separate files** (`coldCallLists.ts`, `winBackCampaign.ts`, `identitySwitcher.ts`, `tabBar.ts`'s PIN modal), each repeating the same boilerplate rather than calling one shared function.
3. A second, differently-named overlay (`follow-up-overlay`) inside the *same* `coldCallLists.ts` file that already has technique #2 — one file, two non-unified modal code paths.
4. An overlay embedded directly in a template string with a `hidden` class (`emailWriter.ts`).

This is the clearest, most fixable evidence of "no shared component system" in the whole audit — four+ ways to do the exact same "show a modal" job, in a codebase with an otherwise well-organized `components/` directory that simply never grew this one primitive.

**Finding 05-12 — two independent progress-bar implementations for the identical visual concept**: Dashboard's Companies House enrich progress uses a real, reusable CSS-class component (`.enrich-progress-track`/`.enrich-progress-fill`, `style.css:3659-3674`); Settings' credit-usage bar reimplements the same concept entirely from scratch with inline styles (`settings.ts:657`, raw `height:4px;width:80px;...border-radius:2px`) instead of reusing the existing classes.

**Finding 05-13 — inconsistent empty-state and loading-state coverage**: one shared `renderEmptyState()`/skeleton-row helper exists (`components/leadTable.ts`) but is used by only 2 of ~15 reachable screens (Dashboard, Cold Call Lists). Every other data-driven screen either shows nothing while loading or a plain "Loading…" text string. This is the single most consistent structural UX gap found: **only 2 of ~15 screens have a real loading affordance**; the rest render blank until data arrives, which reads as "did this break?" to a user on a slow connection or an overloaded backend.

## 5. Error-handling consistency (density/hierarchy of information, applied to failure states)

**Finding 05-14 — silent failure on two screens, masking real outages as "not configured"**: `activityFeed.ts` and `aiProspecting.ts` both swallow fetch failures into an empty/default state with `.catch(() => [])`/`.catch(() => ({...defaults}))` patterns and zero `console.error` calls in either file. AI Prospecting specifically shows "AI Prospecting isn't available because the server doesn't have a Companies House API key configured" identically whether the feature is genuinely unconfigured *or* the backend is simply unreachable — a user has no way to tell "ask an admin to add a key" from "the app is offline" from this screen alone. Contrast with Dashboard and Settings, which consistently use `showToast` or inline error text — this is an uneven pattern across the app, not a universal one, which itself is confusing (some screens tell you when something's wrong, others don't, with no way to predict which in advance).

**Finding 05-15 (positive control)** — Dashboard (`dashboard.ts`) is the reference implementation the rest of the app should be brought up to: a genuine animated skeleton while loading, two distinct empty-state messages (truly-empty pool vs. over-filtered view — most other screens conflate these), and a toast on any load failure. Settings has the best *error-message* handling in the app (19 `showToast` calls, several inline "Failed to load X: {err}" messages rather than generic toasts). These two screens prove the patterns exist and work well in this codebase already — the gap is consistency, not capability.

## 6. Accessibility

**Finding 05-16 — sparse and heavily concentrated, not near-zero but far below what the control count calls for**: across all 17 view files and 7 component files, there are **334 interactive controls** (223 `<button>`, 82 `<input>`, 29 `<select>`) against just **5 `aria-label`s total** (all five in one file, `leadTable.ts`) and **0 `alt=` attributes** anywhere in that scope. 61 of 82 `<input>` elements rely solely on a `placeholder=` as their labeling text — not a reliable accessible name (disappears on focus/input, unsupported as a stable name by all assistive tech). Icon-only close buttons (`✕`) commonly have neither `aria-label` nor `title` (`activityModal.ts:55`), or `title` only, a weaker mechanism than `aria-label` for screen-reader/touch users.

**Finding 05-17 — focus-visible styling actively weakens the indicator on the app's primary keyboard-navigation element**: the sidebar nav's `:focus-visible` rule (`style.css:4795`) replaces the outline with only a low-contrast background-fill change, not a ring — on the one control every keyboard user relies on to move between all ~15 screens. Several other interactive elements (`.inline-edit`, `.ew-body-editor`, `.notes-textarea`, `.ccl-filter-select`) similarly remove the native outline in favor of only a subtle border-color change with no accompanying `box-shadow` ring, while two other elements in the same file (`textarea`, `.search-input`) demonstrate the *better* pattern (border-color change **plus** a visible box-shadow ring) already exists in this codebase — it's just not applied consistently.

**Finding 05-18 — `prefers-reduced-motion` is never checked** (0 occurrences in `style.css`), and at least one JS-driven animation (Dashboard's stat-card count-up, `dashboard.ts:94-113`, an unconditional `requestAnimationFrame` loop) runs regardless of the OS-level reduced-motion preference.

**Finding 05-19 — responsive strategy is minimal but plausibly appropriate**: only 11 `@media` rules total, at seven unrelated, undocumented breakpoints. Given this is a fixed-window desktop app rather than a responsive website, this is defensible as-is rather than a defect — flagged for completeness per the audit brief, not as a priority fix.

## 7. Record-page quality (lead/opportunity records)

The product's closest equivalent to a "record page" is the lead side-panel (`components/sidePanel.ts`) opened from Dashboard/Cold Call Lists/Action Centre, plus the now-unreachable Opportunity Workspace (§1) which was clearly *designed* to be the fuller record-page experience (stage, notes, call log, email drafts, AI intelligence history, and timeline all in one place, per its confirmed imports) but currently cannot be opened by any user. This is the audit's clearest single example of "the pieces for a good record page exist, they're just not assembled into a reachable page" — fixing the routing gap in Finding 05-01 would, by itself, substantially improve record-page quality without writing any new feature code.

## 8. Summary — systemic vs local

**Systemic** (affects the whole product, needs a cross-cutting fix, not a per-screen patch): the two-list routing/IA drift (05-01), type-scale and spacing-scale bypass rates (05-04/05-05/05-06), inline-style-over-CSS-class habit (05-07), the total absence of a shared modal/overlay component (05-11), uneven loading/error-state coverage (05-13/05-14), and thin/unevenly-applied accessibility (05-16/05-17/05-18).

**Local** (contained to one or two files, quick to fix in isolation): the wrong-color danger fallback (05-08), the dead nav-icon palette (05-09), hardcoded chart colors (05-10), the duplicate progress-bar (05-12), and the redundant Settings PIN gate (05-03).

The systemic list is the real answer to "why does it feel homemade" — not any single ugly screen, but the accumulated effect of a token system that exists and is well-designed, being followed inconsistently enough (58% of font sizes, 39% of border-radii, four ways to build a modal) that no two screens quite agree with each other, compounded by three genuinely finished features that vanished from the navigation entirely.
