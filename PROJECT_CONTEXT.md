# Project Overview

CoPilotIQ — a sales-team CRM for cold-calling/prospecting UK companies. Two independent parts in one repo: a chat-based WAT (Workflows/Agents/Tools) framework for manual lookups, and a full desktop CRM app (Tauri + FastAPI backend) that a small sales team uses daily.

# Current Architecture

- `app/` — Tauri desktop app (Rust shell + vanilla TypeScript/Vite frontend). No API keys, no direct Anthropic calls — only talks to the backend over HTTP. Builds macOS/Windows installers via `.github/workflows/release.yml`; ships an auto-updater.
- `backend/` — FastAPI service on the VPS (213.165.88.45), served on port 80 via proxy (8000 is firewalled). Owns all Anthropic API calls, SQLite DB (WAL mode), Companies House integration. Deployed manually via rsync (see CLAUDE.md), not by app releases.
- `workflows/*.md` — five of these are read verbatim as **live backend system prompts** (see CLAUDE.md's "Production AI Prompts" table); two others are chat-only SOPs.
- The chat-based WAT layer (`tools/`, `workflows/` SOPs not listed above, `data/phone_lookups.csv`) is separate from the app/backend and used directly in Claude Code sessions.

# Important Components

- `app/src/style.css` — the authoritative design system (tokens + all styling). `CLAUDE.md`'s Design section summarises it; style.css wins on any disagreement.
- `app/src/views/*.ts` — one file per CRM page (actionCentre=Today, dashboard=Leads, coldCallLists, analytics, winBackCampaign, calendar, activityFeed, aiProspecting, settings). **Outreach (v0.6.24 merge)**: `outreach.ts` is now the single front door — one recipient picker (search+checkbox leads, or pick a whole list) drives everything; `emailWriter.ts` (exactly 1 lead) and `listCampaign.ts` (a list, or 2+ hand-picked leads — same backend pipeline either way) are driven by it via exported handles (`focusLead`/`start`) rather than owning their own pickers. `components/outreachDraftGrid.ts` is the shared bulk draft-review UI both `listCampaign.ts` and (later) anything else can reuse. `sequences.ts` is still a separate sub-tab (folding enrollment into the unified picker is the deferred Phase 2 — see Current Work).
- `app/src/components/topBar.ts` — global top-bar wiring (search, bell, user, nav counts).
- `app/src/connection.ts` — the `/health` poll driving both the offline banner and the sidebar footer status dot.
- `backend/app/db.py` — schema + migrations (`CURRENT_SCHEMA_VERSION` + `MIGRATIONS`, append-only, never edit shipped ones).
- `app/src/*Handoff.ts` — tiny shared-module-state handoffs for cross-view "open this specific thing" jumps (`emailWriterHandoff`, `dashboardFilterHandoff`, `opportunityWorkspaceHandoff`, `coldCallListHandoff`). Same pattern each: `setPendingX`/`consumePendingX`, consumed via `subscribeTabs` in the target view.
- `audits/` — point-in-time OS-audit reports checking whether this repo's own docs/memory match reality. Not code; read-only reports.
- `audit/` — distinct from `audits/` above: the 2026-08-12 full product/SaaS-readiness audit (11 docs + reusable scan scripts + JSON results) and its derived `implementation-spec-stage-0.md`. Source of truth for the roadmap currently being executed — see Current Work.
- `backend/app/services/token_crypto.py` — Fernet encryption for OAuth tokens at rest (`TOKEN_ENCRYPTION_KEY`, required setting, no default).

# Data / Database

SQLite at `/opt/v1-agent/backend/data/team.db` on the VPS, WAL mode. Migrations run automatically on backend restart. Companies House filing feed self-prunes to 30 days. Shared lead pool by default — leads outside a list are visible/editable to all users (deliberate).

# Integrations

- Anthropic API (backend only, `backend/.env`)
- Companies House: **two** separate keys — `COMPANIES_HOUSE_API_KEY` (REST, prospecting) and `COMPANIES_HOUSE_STREAM_KEY` (Streaming, live filing feed)
- Mailchimp export (Today page, pending email drafts)
- LinkedIn (chat-tool only, `tools/post_to_linkedin.py` + `linkedin_oauth_setup.py`, credentials via root `.env`)

# Known Issues

- **RESOLVED: AI email generation 502 in production (2026-08-18).** Was never transient — `generate_email`/`refine_email`'s `EXTRACTION_SCHEMA` had `minimum`/`maximum` on its three `number` fields, which Anthropic's structured-output schema validation rejects outright (400 every single call: "properties maximum, minimum are not supported"). Only found this because the swallowed-exception logging fix above finally surfaced the real traceback. Fixed by dropping those two keywords (the 0-1/0-100 range is still communicated via the prompt text, just not schema-enforced) — pushed, needs the usual backend deploy to take effect. Worth a final live test after deploying: generate an email for a real lead and confirm it actually returns content this time.
- No Apple notarization (Gatekeeper "damaged app" on new Macs) — needs Apple Developer Program.
- **No HTTPS for the app's main API traffic** — the desktop app's `BACKEND_BASE_URL` (baked in at CI build time) is still `http://213.165.88.45`, plain HTTP to the IP; unrelated to the OAuth fix below and still needs a real domain to fix properly.
- **DB backups exist but only fire on a schema migration** (`db.init_db()`'s automatic pre-migration backup, `BACKUP_RETENTION_COUNT=10`, uncompressed) — never on a plain restart, so real calendar-based coverage is missing between deploys. `backend/deploy/backup.sh` (cron, gzip'd, `KEEP=14`) was written to fill exactly this gap and was never installed — see Current Work / Stage 0.
- **Production DB grew 58MB→1.68GB (~29x) in one month — real lead found (2026-08-18), not yet confirmed.** Deploying migration 033's `CREATE INDEX` on `ch_charge_feed` (the CH filing feed) took several genuinely CPU-bound minutes against the live 1.68GB DB — strongly suggestive that table is the bulk of the growth, despite its documented 30-day self-prune. Next step: `SELECT COUNT(*) FROM ch_charge_feed` on the VPS to confirm, then check whether the prune is actually running/working.
- Win-back emails have no unsubscribe link (blocked on domain/HTTPS).
- **Google OAuth (email connect): RESOLVED and live in production (2026-08-17).** Google rejects bare-IP redirect URIs (needs a real domain + HTTPS) — fixed without buying one: VPS nginx (`/etc/nginx/sites-enabled/phone-lookup-backend`) serves HTTPS on the free wildcard-DNS hostname `213-165-88-45.sslip.io` via Let's Encrypt (certbot, auto-renews); `PUBLIC_BASE_URL=https://213-165-88-45.sslip.io` + `GOOGLE_OAUTH_CLIENT_ID`/`SECRET` are set directly in the VPS `.env` (not a code deploy, already live). Verified: Connect Gmail reaches Google's real consent screen. Dedicated to this CRM only — the user's real domain purchase is for a separate, unrelated SaaS. Microsoft/Outlook not yet configured (same pattern, optional). **Watch for on any future certbot run on this file**: it previously moved every `location` block onto the new port-443 block and left port 80 (the app's real `BACKEND_BASE_URL` traffic, plain IP) 404ing everything — fixed by duplicating the `location` blocks back onto port 80, redirecting to HTTPS only when `$host` matches the sslip.io hostname specifically. Re-verify `curl http://213.165.88.45/health` after any future certbot edit to this file — not automatic.
- **Activity Feed name/number: RESOLVED and deployed (2026-08-11), verified live.** Two stacked bugs: (1) `COMPANIES_HOUSE_API_KEY` on the VPS was itself invalid — user rotated it, confirmed 200 via direct test. (2) `main.py` was passing a single key into `run_filing_stream()` for both the Streaming connection and the per-event REST follow-ups inside `_process_event()`, which need the separate, non-interchangeable `COMPANIES_HOUSE_API_KEY` — so the REST key was never actually used regardless of validity. Fixed by threading `stream_key`/`rest_api_key` through as distinct params. Deployed; confirmed live: resolved-name count jumped from 30 to 200+ within two minutes of restart, fresh rows showing real names. Also fixes AI Prospecting's CH enrichment, which shares the key path via `activity_refresh_service.py`.
- **New from the above fix, DEPLOYED**: once the charge feed could actually use `COMPANIES_HOUSE_API_KEY`, it started drawing enough volume (several events/sec, up to 2 REST calls each) to exhaust the whole account-wide CH rate limit (~600/5min) and 429 everything else sharing the key. Fixed with a 2s minimum-interval throttle scoped to just the stream's own REST calls (`ch_stream_service.py`), not a global limiter.
- **Backend deploy process gap, fixed 2026-08-18**: the documented deploy command only ever rsynced `backend/app/`, never `backend/requirements.txt` (a separate path) — so a new Python dependency (`sentry-sdk`, added weeks earlier for Stage 0) silently never installed on the VPS, crash-looping the service on the next deploy. CLAUDE.md's deploy command now always syncs + `pip install`s requirements.txt (a no-op when nothing changed). Also learned: a deploy carrying many queued migrations at once against a large real DB can legitimately take several minutes, not the usual ~30s — don't restart mid-migration.
